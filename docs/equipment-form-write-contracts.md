# EquipmentForm: контракты чтения и записи

Документ фиксирует фактические контракты legacy перед реализацией Clayzor. Источники:
`Kesco.Lib.Entities/Corporate/Equipments/Equipment.cs`, `Kesco.Lib.Entities/SQLQueries.cs`,
`Inventory/Equipment/Equipment_form.aspx.cs` и профильные вспомогательные формы в
`C:\CLAYZOR-KIMI\Kesco.App.Web.V4.Inventory`.

Статусы: **подтверждено** — найден конкретный SQL и порядок вызовов; **требует анализа** — реализацию
нельзя начинать по догадке; **требует проверки инфраструктуры** — SQL известен, но внешний сервис или
его доступность ещё не подтверждены.

## Основная запись оборудования — подтверждено

### Чтение

`SQLQueries.SELECT_ID_Оборудование` читает `vwОборудование.*`, название и PN модели, тип, текущего
сотрудника (`До IS NULL`) и последнее расположение. Расположение выбирается условием отсутствия более
поздней записи `ОборудованиеРасположение.От`.

При переносе нельзя предполагать, что у оборудования всегда есть расположение: внешнее соединение с
расположением и сотрудником должно быть безопасным для неполных данных. Отдельно проверяется фактическая
схема `vwОборудование`, чтобы не опираться на `SELECT *` в новой модели.

### Валидация

`ValidateTypeConfig` перед записью проверяет:

- документ списания требует дату списания;
- для всех типов, кроме SIM-карты, непустая дата списания требует документ списания;
- владелец обязателен;
- тип обязателен (в legacy сообщение ошибочно называет его моделью; в Clayzor сообщение должно быть точным).

`ValidateMACConfig` вызывается только если тип поддерживает MAC. Legacy удаляет все не-hex символы и
проверяет длину 12. Clayzor сохраняет более строгий уже принятый контракт `EquipmentIns`: разрешены только
hex-символы и разделители пробел/двоеточие/дефис/точка; после нормализации допустимы пустое значение или
ровно 12 hex-символов. Недопустимые символы не должны молча исчезать и превращаться в валидное значение.

Дату и время списания необходимо преобразовывать из компонентов локального времени браузера в UTC в часовом
поясе браузера. Нельзя повторять старый расчёт через смещение уже сконструированного UTC-момента: он ошибается
на границах DST. Пустая дата в legacy представляется `DateTime.MinValue`; в новой модели следует использовать
`null`, если фактическая схема и триггер это подтверждают.

### UPDATE

`SQLQueries.UPDATE_Оборудование` выполняет параметризованный `UPDATE vwОборудование` по
`@КодОборудования`. Набор ровно из 15 изменяемых полей:

| Параметр | Поле |
|---|---|
| `@SN` | серийный номер |
| `@ПодключенаКамера` | признак подключённой камеры |
| `@Списано` | дата и время списания |
| `@КодДокументаСписания` | документ списания |
| `@СетевоеИмя` | сетевое имя |
| `@MACадрес`, `@MACадрес2`, `@MACадресILO` | три MAC-адреса |
| `@Примечания` | примечание оборудования |
| `@КодЛицаВладельца` | владелец |
| `@КодЛицаАрендатора` | арендатор |
| `@КодЛицаПоставщика` | поставщик |
| `@КодПулаТелефонов` | телефонный пул |
| `@КодМоделиОборудования` | модель |
| `@КодДокументаПоступления` | документ поступления ОУ |

В этом `UPDATE` нет даты поступления, начального расположения/ответственного, бухгалтерского поступления,
должности и отдельных полей SIM/компьютера/маршрутизатора. Их нельзя добавлять в основной UPDATE без отдельно
подтверждённого контракта.

`Equipment.Save(false)` открывает `TransactionScope` с `ReadCommitted`, выполняет UPDATE, затем изменения
телефонов и запрошенные побочные операции; только после этого вызывает `Complete()`. В Clayzor нужна одна
явная SQL-транзакция на соединении для основной записи и телефонного diff. Внешние сетевые/АТС-вызовы нельзя
незаметно помещать внутрь длительной SQL-транзакции: их порядок и компенсация должны быть зафиксированы отдельно.

После обычного сохранения legacy обновляет текущую форму либо закрывает её с `returnValue=1`. Clayzor должен
после успешного сохранения обновить данные формы и существующий родительский грид через callback, без
`location.reload()`. Повторный Save не должен выполняться параллельно с уже идущим сохранением.

## Телефоны оборудования — SQL и получатели синхронизации подтверждены

Чтение: `SELECT * FROM dbo.fn_НомераТелАппаратов(@КодОборудования) ORDER BY Основной DESC, Описание`.

Выбор нового номера использует `fn_НомераДляТелАппаратов(@LocationId, @EmployeeId, @EquipmentTypeId,
@PhoneIdBase, @EquipmentId)` и исключает ID текущего списка через отдельные Dapper-параметры. Поисковый текст
и `LimitPlusOne` остаются серверными; выбранное ранее значение восстанавливается по ID без фильтра текущего списка.

Внутри той же транзакции, что и основной UPDATE, форма сравнивает текущие строки со списком формы:

1. Удаление отсутствующих связей:
   `DELETE FROM ТелефонныеНомераОборудование WHERE КодТелефонногоНомера=@КодТелефонногоНомера AND КодОборудования=@КодОборудования`.
2. Обновление только изменённых существующих связей:
   `UPDATE ТелефонныеНомераОборудование SET СрокВозврата=@СрокВозврата, Примечание=@Примечание WHERE КодТелефонногоНомера=@КодТелефонногоНомера AND КодОборудования=@КодОборудования`.
3. Добавление новых связей вместе с уже введёнными сроком и примечанием:
   `INSERT INTO ТелефонныеНомераОборудование (КодТелефонногоНомера,КодОборудования,КодОборудованияПодключения,СрокВозврата,Примечание) VALUES (...)`.

Ключ связи составной: телефон + оборудование. Для новой записи `КодОборудованияПодключения=0` преобразуется
в `NULL`. Срок возврата и примечание редактируются отдельным диалогом; изменение этих полей не должно
пересоздавать связь. Неизменённая общая строка не включается в UPDATE, чтобы не перезаписывать чужие правки.

Если тип поддерживает телефонные номера, после diff legacy запускает синхронизацию удалённых и текущих номеров:

- для Xorcom — `Phone.Xorcom_Sync`;
- для CCM — `Equipment.CCM_Sync`, который вызывает `SQLQueries.SP_PhoneSync_CCM` как хранимую процедуру и
  анализирует `@RETURN_VALUE`;
- дополнительно синхронизируются связанные аппараты и оборудование подключения.

Состав получателей подтверждён по legacy `SynchronizeFillLists`: другие аппараты с тем же номером дополнительно
не ищутся. Для CCM синхронизируются уникальные `ConnectionEquipmentId` из исходного и текущего списков; текущее
оборудование добавляется только при отсутствии таких получателей. При смешанном наборе станций сохраняется приоритет
legacy: при наличии Xorcom-номеров ветка CCM не выполняется. Оба порядка покрыты профильными тестами. Фактические
вызовы АТС в тестах не выполняются. Особое поведение legacy, подавляющее исключение при `PerformSynchronize`, в
Clayzor не переносится: частичный успех явно показывается пользователю и отличается от успешной SQL-записи.

## UPS — CRUD связей и тестов подтверждён

На форме сервера список подключённых UPS читается из `vwПодключенияUPS` по
`@КодОборудованияСервера`, с названием модели, SN, сетевым именем и PN. Быстрое подключение выполняется
параметризованным INSERT пары `@КодОборудованияUPS + @КодОборудованияСервера` с `НастроеноВыключение=0`.
Выбор ограничен оборудованием типа UPS; после INSERT список перечитывается.

Полная форма `LinkUps` редактирует UPS в обратном направлении — список серверов выбранного UPS и тесты.
Серверный diff сравнивает текущий список БД со списком формы:

- отсутствующие пары удаляются по `КодОборудованияUPS + КодОборудованияСервера`;
- у существующих меняется только `НастроеноВыключение`;
- новые пары добавляются вместе с этим признаком.

Тесты UPS идентифицируются `КодТестирования + КодОборудованияUPS`; INSERT/UPDATE сохраняют дату тестирования,
время батарей, список получивших оповещение серверов и ошибки. Удаление тестов намеренно отключено требованием
legacy. Все изменения серверов и тестов сохраняются одной транзакцией. Legacy строит batch с форматированием
чисел и параметрами только для части значений; Clayzor должен параметризовать **все** ID, даты, время, числа и
строки, сохранив тот же diff и порядок, без копирования небезопасного построения SQL.

После сохранения вспомогательной формы обновляются UPS-сведения родительской карточки. Отмена диалога не должна
менять БД: до Save списки существуют только в состоянии формы.

## Сеть и специальные операции — точные контракты

### Подключение/отключение рабочей сети — SQL подтверждён

Текущее состояние читается из `vwЛокальнаяСетьПрисоединениеРабочейСети` по оборудованию с `Открыто<>0`.
Если записи нет, оборудование считается не подключённым; если есть, сохраняется счётчик `Открыто`.

Команда attach выполняет `INSERT vwЛокальнаяСетьПрисоединениеРабочейСети (КодОборудования)
VALUES (@КодОборудования)`. Detach после подтверждения выполняет `UPDATE ... SET Открыто=0 WHERE
КодОборудования=@КодОборудования AND Открыто>0`. Это SQL-операции, а не произвольный внешний сетевой API.
После команды состояние перечитывается. В legacy команда объединена с сохранением основной формы; в Clayzor
сначала валидируются и сохраняются основные поля, затем в той же согласованной операции выполняется сетевой
запрос, а результат и возможная частичная ошибка явно показываются пользователю. Повторный клик блокируется.

### WakeOnLan — инфраструктурный блокер

Legacy вызывает `sp_WakeOnlan` с `CommandType.StoredProcedure` и единственным параметром `@СетевоеИмя`.
В базе `Инвентаризация` текущего стенда `OBJECT_ID(N'dbo.sp_WakeOnlan')` возвращает `NULL`, поэтому операция
не реализована и не имитируется. После добавления процедуры нужно потребовать непустое сетевое имя, сохранить
форму либо запретить команду и проверить фактический результат на тестовом оборудовании.

### Конфигурация IP-телефона — подтверждено

Команда доступна для типа 30. Перед открытием форма должна быть сохранена, указаны MAC и телефонный пул, а в
модели задан шаблон конфигурации. Clayzor открывает `/Equipment/PhoneConfigHandler.ashx?mac=<MAC>` в новом окне.
Endpoint проверяет роль 102 и вызывает `sp_КонфигурацияIpТелефона` с output-параметром конфигурации. Реальный
ответ проверен как XML с корнем `gs_provision`; содержимое конфигурации и секретные данные не журналируются.

### Ping — внешний endpoint

Legacy опрашивает `/inventory/ping.ashx?host=<url-encoded>` каждые пять секунд, только если сетевое имя найдено
в локальной сети. Имя, начинающееся с `*`, не опрашивается; из составного имени берётся часть после последнего
`\`. В Clayzor polling должен останавливаться при disposal/смене записи, игнорировать поздние ответы и не
показывать устаревший статус. До подтверждения доступного серверного endpoint кнопка/индикатор не считаются
реализованными; не следует имитировать ping случайным или постоянным состоянием.

### Детализация SIM — инфраструктурный блокер

Кнопка появляется для SIM оператора Билайн (`КодЛицаИсполнителя = 908`). Сервер дополнительно проверяет наличие
текущего ответственного и признак `Подчинённый`: роли 41/42 по заказчику либо наличие тарификации у
подчинённых сотрудников. В URL передаются сотрудник, договор, телефон, параметры НДС, оформление и режим
текущего месяца. Фактический `URI_accounting_phone_form` и приложение тарификации в текущем окружении
отсутствуют, поэтому адрес не выдумывается и операция не объявляется реализованной.

### Копирование и истории — read-only/навигация

«Копировать» открывает уже реализованный `/Equipment/EquipmentIns?copyId=<ID>`; штатное создание остаётся только
через `sp_Оборудование_Ins`. Табличные части при этом не копируются автоматически.

История сетевых имён читается из `vwОборудованиеСетевыеИмена` с сотрудником, сортировка `Изменено DESC`.
Кнопка «История имён» открывает read-only диалог с локальным временем; открытие и закрытие диалога не меняют
несохранённые поля основной формы. Последняя инвентаризация — последняя по `ВремяПроверки` строка `vwРеальноеРасположениеОборудования`; выводятся
дата, сотрудник, признак неремонтопригодности, примечание и предупреждение о расхождении фактического и
учётного расположения. Это read-only данные, не поля основного UPDATE.

Отдельный JS-метод `editReturnPeriod` в актуальном legacy пуст. Поэтому его нельзя считать работающим контрактом.
Сроки возврата реализуются через уже подтверждённые UPDATE телефонной связи, расположения и ответственного,
с явным выбором конкретной строки и последующим обновлением соответствующей секции.


## Расположения — SQL подтверждён

Чтение истории: `SELECT_ОборудованиеРасположение_КодОборудования` возвращает дату `От`, расположение,
срок возврата, примечания и сведения `Изменил/Изменено`, упорядоченные по `От`. Текущая запись — запись,
для которой нет более поздней `От`.

Добавление использует `INSERT_ОборудованиеРасположение` с параметрами `@КодОборудования`, `@От`,
`@КодРасположения`, `@СрокВозврата`, `@Примечания`. Запрос отказывается вставлять запись, если уже появилась
более поздняя (`RAISERROR`), что является проверкой concurrency. Дополнительно тот же SQL для не списанной
телефонной станции типа 28 с сетевым именем переносит новое расположение на связанные SIM типа 27, у которых
примечание текущего расположения начинается с этого сетевого имени. Этот side effect является частью
контракта; заменять запрос простым INSERT нельзя.

Редактирование существующей строки меняет только `СрокВозврата` и `Примечания`; `От`, время и расположение
в режиме редактирования заблокированы. Ключ WHERE — оборудование и `От` с отсечёнными миллисекундами.
В новой модели нужно хранить исходный момент `От` отдельно от отображаемого локального времени.

Проверки формы: расположение, дата и время начала обязательны; нельзя повторно назначить текущее расположение;
дата начала в будущем отклоняется; срок возврата обязателен при включённом признаке, не раньше даты начала и
не позднее текущей даты плюс три месяца. Если новое расположение — «На руках» (55) и нет действующего
ответственного, в той же транзакции дополнительно создаётся ответственный с тем же `От`.

В `LocationEquipment.Save` выражение `DateReturn ?? DateReturn.Value.Date` является legacy-дефектом и при
`null` обращается к `Value`. В Clayzor необходимо передавать настоящий `DBNull`/Dapper `null`, не воспроизводя
эту ошибку. В гриде legacy есть добавление и редактирование, но нет команды удаления; самостоятельно добавлять
DELETE истории нельзя без нового требования и проверки связанной логики.

## Ответственные — SQL подтверждён

Чтение истории: `SELECT_ОборудованиеСотрудники_КодОборудования` возвращает `От`, `До`, сотрудника,
срок возврата, примечания и `Изменил/Изменено`, упорядоченные по `От`. Форма редактирования загружает текущего
ответственного (`До IS NULL`) либо последнюю запись, если действующего нет.

Добавление: `INSERT INTO ОборудованиеСотрудников (КодОборудования,От,КодСотрудника,СрокВозврата,Примечания)`
с соответствующими параметрами. Обновление меняет только `До`, `СрокВозврата`, `Примечания` по составному
ключу оборудование + `От`, нормализованный до секунд. Как и для расположений, исходный `От` должен оставаться
ключом записи и не пересчитываться через часовой пояс.

Форма поддерживает три разные операции:

- **выдать** — добавить нового ответственного с обязательными сотрудником, датой и временем `От`;
- **изъять** — закрыть текущую запись через `До`; при необходимости можно сразу добавить следующего;
- **изменить сведения** — обновить только срок возврата и примечание существующей записи.

Срок возврата проверяется аналогично расположению: не раньше начала периода и не позднее трёх месяцев от
текущей даты. При изъятии оборудования, находящегося «На руках» (55), форма требует новое расположение, не
равное 55, и создаёт его с `От = До` в одной транзакции с изменением ответственного. При выдаче и изъятии
связанные секции расположений и ответственных должны обновляться вместе без перезагрузки всей формы.

Найденная в тестовой БД процедура `sp_Смена_ответственного_за_оборудование` **не используется** этими legacy
формами и потому пока не является подтверждённым заменяющим контрактом. В гриде нет удаления истории.
Здесь также присутствует дефект `DateReturn ?? DateReturn.Value.Date`; новый код должен безопасно передавать
`NULL`.

Для обеих вспомогательных форм явных `HasRole` в их codebehind нет. Наследуемые проверки `EntityPage` и правила
доступности кнопок в `Kesco.Equipment.js` ещё требуют анализа; отсутствие локальной проверки не означает
разрешение записи всем пользователям.

## Учётные записи — CRUD подтверждён

Источник — `vwОборудованиеУчётныеЗаписи`; составной ключ: `@КодОборудования + @Логин` (`varchar(50)`).
Список читается `SELECT ... WHERE КодОборудования=@КодОборудования ORDER BY Логин`, одиночная запись —
с дополнительным условием `Логин=@Логин`.

- INSERT записывает `КодОборудования, Логин, Пароль, ОграниченныеПрава, Примечание`.
- UPDATE по составному ключу меняет `Пароль, ОграниченныеПрава, Примечание`; логин после создания read-only.
- DELETE выполняется по тому же составному ключу после подтверждения пользователя.

Размеры по legacy-модели: логин 50, пароль 128, примечание 300; `ОграниченныеПрава` — `tinyint`.
Дополнительной бизнес-валидации в форме нет, но новая форма должна как минимум требовать непустой логин и
ограничивать длины до обращения к БД.

Пароли в legacy реально хранятся и возвращаются из представления. В гриде показывается маска `*****`, а по
команде `ShowPwd` выполняется отдельное чтение одиночной записи и значение вставляется в DOM. В Clayzor не
следует загружать пароли в общую модель списка: список должен содержать только логин, признак прав и примечание.
Показ и редактирование пароля требуют отдельного авторизованного запроса по ключу; пароль нельзя включать в
URL, журнал, сообщения об ошибках, тестовые выводы или callback родительскому гриду. Поле ввода — password,
по умолчанию скрытое. Это сохраняет функциональность legacy без лишнего раскрытия секретов.

## Компьютер — дневной UPSERT подтверждён

История читается `SELECT_Компьютеры_КодОборудования`: все поля `Компьютеры`, ФИО изменившего и названия двух
стандартных конфигураций, сортировка по `С`. Для редактирования выбирается последняя запись
(`SELECT TOP 1 ... ORDER BY С DESC`). Если её `С` не равна текущей дате, форма использует значения как шаблон,
но сохраняет новую запись на текущую дату. Таким образом это не перезапись всей истории, а UPSERT дневного
снимка по ключу `КодОборудования + С`.

`UPDATE_Компьютеры` — единый параметризованный SQL-batch: при существовании ключа UPDATE, иначе INSERT.
Записываются `RAM/RAMDetail`, `HD/HDDetail`, `SSD/SSDDetail`, две пары стандартной конфигурации и даты,
`Лицензия`, `Примечания`. Отдельной транзакции вокруг batch legacy не создаёт; DELETE и редактирование
произвольной исторической строки в гриде нет, есть только добавление/актуализация текущего снимка.

Детали памяти и дисков сериализуются через `+`. RAM — целые Мб, число банков ограничено характеристикой модели
`MemoryBanks`; HD — число Гб (legacy `double`/`real`), SSD — целые Гб. Пользователь может добавлять HD и SSD,
значения неотрицательны; итоговые поля равны сумме компонентов. Перед сохранением удаляются нулевые хвосты
всех трёх detail-строк. В новой модели следует хранить компоненты списком чисел и централизованно сериализовать/
разбирать их, не дублируя ручной разбор в разметке. Нужны профильные тесты пустых строк, нулевых хвостов,
дробных HD и сумм.

Валидация конфигураций:

- выбранная конфигурация 1 требует дату 1;
- конфигурация 2 требует дату 2, а также конфигурацию и дату 1;
- дата без соответствующей конфигурации запрещена;
- обе даты не могут быть в будущем;
- очистка конфигурации очищает её дату.

## SIM-карта — UPSERT, удаление и списание дубликата подтверждены

На одно оборудование приходится не более одной записи `vwSIMКарты` с ключом `КодОборудования`. Если записи
нет, грид показывает добавление; иначе — редактирование и удаление. `UPDATE_SIMКарты` является SQL-batch
UPSERT: UPDATE существующей строки либо INSERT новой.

Записываются `НомерТелефона`, `От`, `КодДоговора`, `КодЛицаПерсональныхДанных`, `PIN`, `PIN2`, `PUK`, `PUK2`.
Обязательны номер, дата/время активации и договор связи. Номер — только цифры; PIN — ровно 4 цифры, PIN2 —
4–8 цифр, PUK и PUK2 — ровно 8 цифр. Дата и время активации преобразуются из локального времени браузера в UTC
с корректной обработкой DST. Пустые идентификаторы договора/лица ПДн передаются как `NULL`, пустые PIN/PUK —
как пустые строки согласно NOT NULL-схеме.

PIN/PUK являются секретами так же, как пароли учётных записей: их нельзя писать в журналы, URL, ошибки и
отладочные снимки. Общий список не должен неоправданно переносить эти значения в клиентскую разметку.

Договор выбирается среди незавершённых мобильных договоров. Лицо ПДн зависит от договора, оборудования и
технических тарифов. Legacy проверяет: для юрлица совпадение с заказчиком и наличие технического тарифа; для
физлица — совпадение с заказчиком либо должность сотрудника у заказчика. Есть действие «Заполнить» лицо ПДн
из текущего ответственного сотрудника. Эти справочные запросы должны быть перенесены отдельно до реализации
зависимого контрола, не заменяя их произвольным списком всех лиц.

Перед сохранением ищется другая не списанная SIM с тем же номером
(`SELECT_SimКарты_Другая_С_Тем_Же_Номером`). После явного подтверждения другая SIM списывается моментом
активации текущей (`UPDATE vwОборудование SET Списано=@Списано`), затем сохраняется текущая запись. В legacy
это два отдельных вызова без общей транзакции; Clayzor должен выполнить подтверждённое списание и UPSERT в
одной SQL-транзакции, чтобы ошибка второго шага не оставила частичный результат. При копировании лица ПДн из
старой SIM применяется только если у текущей оно не выбрано.

DELETE удаляет только сведения SIM по `КодОборудования`, а не само оборудование. После всех операций обновляется
секция SIM; при изменении номера должна также обновиться секция допуслуг, поскольку её связь строится по номеру.

## Дополнительные услуги SIM — INSERT/UPDATE подтверждены

История читается из `vwSIMКартыДопУслугиСотОператора` по номеру телефона текущей SIM. Параметры
`@ПоказатьИсторию` и `@ПоказатьОбязательные` управляют фильтрами. Запись идентифицируется
`@КодSIMКартыДопУслугиСотОператора`. Отдельного DELETE в форме нет: прекращение услуги выражается датой `До`.

Если номер не передан, SQL получает его по `@КодОборудования`; при невозможности однозначно определить номер
вызывается `RAISERROR`. Для новой записи INSERT, для существующей UPDATE по ID. Записываются фактические `От`,
`До`, тип и название услуги и три стоимости; при INSERT `Сохранено=GETUTCDATE()`.

Даты окончания в БД эксклюзивные: при сохранении выбранная пользователем включительная дата увеличивается на
один день, при чтении уменьшается на день. То же относится к плановым датам в модели, однако в актуальном SQL
`ОтПлан` и `ДоПлан` закомментированы и **не сохраняются**. Нельзя заявлять, что плановые даты записаны, пока
отдельно не подтверждён и не включён безопасный контракт их сохранения.

SQL отклоняет пересекающуюся услугу с тем же номером, типом и названием. В форме обязательна фактическая или
плановая дата подключения и тип/название услуги; начало не позже окончания, фактические даты не в будущем,
плановые — строго в будущем. При создании тип и название доступны, стоимости берутся из выбранного типа и
заблокированы; при редактировании тип/название read-only, стоимости доступны. Стоимости выводятся с двумя
знаками, в БД — `money`.

Проверку пересечений и границ дат нужно покрыть тестами, включая открытый интервал `До=NULL`; нельзя без
проверки копировать потенциальный пробел условия `@До > От` для открытого нового интервала.

## Лицензия — UPSERT подтверждён

Лицензия хранится в `vwSoft` с ключом `КодОборудования`, одна запись на оборудование. Список показывает добавление
при отсутствии записи и редактирование при наличии; DELETE отсутствует. `UPDATE_Soft` — SQL-batch UPSERT.

Поля: тип лицензирования, номер лицензиата, URL проверки, количество серверов и клиентов, `ДействуетОт`,
`ДействуетДо`, дистрибутив. Тип лицензии обязателен и определяет видимость/обязательность полей:

- при `Resale=0` показан и обязателен номер лицензиата;
- при `Temporary<>0` обе даты обязательны и начало не позже окончания;
- количество серверов обязательно (legacy допускает 0);
- количество клиентов обязательно и должно быть ненулевым.

`ДействуетДо` также хранится как эксклюзивная граница: `+1 день` при записи и `-1 день` при чтении.
Скрытые по типу лицензии значения не должны нечаянно сохраняться как будто пользователь их подтвердил;
правила очистки/сохранения нужно покрыть тестами на смену типа.

## Установленное ПО — INSERT/UPDATE подтверждены

Записи хранятся в `vwОборудованиеПО`, ключ — `@КодОборудованияПО`. История читается с названием,
дистрибутивом, примечаниями, признаком деинсталляции и `Изменил/Изменено`, сортировка по `От`.

INSERT записывает `КодОборудования, КодПО, От, До, Установлено, Дистрибутив, Примечания`.
UPDATE по `КодОборудованияПО` разрешает изменить все эти поля. Физического DELETE нет: удаление ПО
фиксируется датой `До` и требует отдельного подтверждения, что ПО действительно полностью удалено.

Обязательны дата установки, выбранное ПО и дистрибутив. Выбор ПО — это выбор другого оборудования с признаком
`IsSoft`; его модель автоматически заполняет `Установлено`. Размеры legacy: `Установлено` и `Дистрибутив`
по 100 символов, примечания 300. Дата установки не должна быть позже деинсталляции.

Грид и одиночное чтение преобразуют `До` через `DATEADD(day,-1,До)`, а UPDATE сохраняет `+1 день`, то есть
использует эксклюзивную границу. INSERT передаёт `@До` без `+1` — это несогласованность legacy. В Clayzor нужна
единая функция преобразования включительной даты UI в эксклюзивную дату БД для обоих путей и обратно, с тестами
создания и редактирования. Также в legacy есть опечатки валидации: повторная проверка даты вместо обязательности
ПО и неверное условие сравнения дат. Их не следует воспроизводить.

После сохранения обновляется только секция ПО; ссылка по `КодПО` открывает карточку соответствующего
оборудования, а не путает её с `КодОборудованияПО`.

## Бухгалтерский учёт — CRUD и права требуют раздельной реализации

История `ОборудованиеБухУчета` читается с бухгалтерией-владельцем, арендатором, материалом/инвентарным номером,
датами поступления и списания, примечаниями и `Изменил/Изменено`. Ключ записи —
`@КодОборудованияБухУчета`.

INSERT и UPDATE используют один набор параметров: оборудование, лицо бухгалтерии, признак `Материал`,
арендатор, инвентарный номер, `От`, документ поступления, `До`, документ списания, примечания.
Для материала перед записью принудительно очищаются арендатор и инвентарный номер. Для основного средства
инвентарный номер обязателен, арендатор доступен. Всегда обязательны владелец, тип материала и дата поступления.
Выбранный документ списания должен быть доступен текущему пользователю.

Справочник владельца ограничен лицами с бухгалтерским учётом. Документы поступления ограничены актами
приёма-передачи, ТТН, счетами-фактурами и инвойсами; документы списания — актами приёма-передачи/списания с
потомками и синонимами, ТТН и счетами-фактурами. Оба списка должны фильтроваться выбранным владельцем; его смена
очищает оба документа. В legacy `dbsDocumentReceipt_BeforeSearch` ошибочно добавляет владельца в фильтр документа
списания вместо поступления. В Clayzor следует исправить эту фильтрацию и проверить её тестом.

Существует SQL удаления последней по `От` записи оборудования и активные команды `Delete_Accounting` в C#/JS,
но кнопка удаления грида в актуальной legacy-разметке закомментирована. Если реализовывать удаление для
требуемого CRUD, использовать именно подтверждённый `DELETE ... WHERE КодОборудованияБухУчета IN (SELECT TOP 1
... ORDER BY От DESC)`, с подтверждением и серверной проверкой права; нельзя удалять произвольную строку по ID,
подменяя этот контракт. Доступность бухгалтерского блока должна проверяться ролями 66/68 по владельцу и
`fn_БухгалтерскийУчет`, как в принятом `EquipmentIns`, а не только скрытием кнопок.

После добавления/изменения/удаления обновляются секция бухучёта и связанные поля основной формы
(владелец/арендатор/документы), без потери несохранённых остальных полей.

## Маршрутизатор — подтверждён только read-only контракт

Основные сведения читаются из `vwRouters` по `КодОборудования`; описание выводится над таблицей. Строки секции
читаются из `vwRoutersInventory WHERE КодОборудования=@КодОборудования ORDER BY Код`.

В `Equipment_form.aspx.cs` у `gridRouter` отключены сервисные колонки, а в `EquipmentRouter` нет Save/Delete.
INSERT/UPDATE/DELETE для этих представлений в legacy-контракте формы отсутствуют. Поэтому секция маршрутизатора
в Clayzor должна быть полноценным read-only представлением существующих данных, без фиктивных кнопок CRUD.
Появление редактирования потребует отдельного подтверждённого источника записи и не должно блокировать чтение.

| Срез | Статус записи | Обязательный результат анализа |

| Ответственные | SQL подтверждён | проверить права EntityPage/JS, составные операции и реальный CRUD |
| Учётные записи | CRUD подтверждён | реализовать отдельное авторизованное чтение секрета и проверить реальный CRUD |
| Компьютер | дневной UPSERT подтверждён | проверить схему/триггеры, сериализацию компонентов и реальный CRUD |
| SIM | UPSERT/DELETE подтверждены | справочники договора/ПДн, атомарное списание дубликата, реальный CRUD |
| Дополнительные услуги SIM | INSERT/UPDATE подтверждены | границы дат, пересечения, плановые поля и реальный CRUD |
| Лицензия | UPSERT подтверждён | типы лицензирования, границы дат и реальный CRUD |
| ПО | INSERT/UPDATE подтверждены | единые границы `До`, справочник ПО, реальный CRUD |
| Бухгалтерский учёт | INSERT/UPDATE/DELETE последней записи подтверждены | права, фильтры документов, связанный refresh, реальный CRUD |
| Маршрутизатор | read-only подтверждён | проверить фактические представления и отображение |
| UPS | CRUD связей и INSERT/UPDATE тестов подтверждены | параметризованный diff, транзакция и реальный CRUD |

Для каждого среза до кода должны быть записаны конкретные SELECT/INSERT/UPDATE/DELETE или процедура,
параметры, транзакционные границы, роли, операции обновления связанных секций и способ проверки на реальной БД.
